## Unique discoveries — read this before your next Playwright verification pass here

0. **(Session 2, 2026-07-29) A real production rendering bug that only reproduces on the actual Xibo hardware, never in a normal browser — and CSS `:has()` was the reason.** The user noticed the "Kuliah Khas" purple day-cell and "Bacaan Yasiin & Tahlil" green day-cell highlights weren't showing on the physical Xibo signage screen, even though they render correctly in any modern desktop browser and always had. Root cause: both highlights were implemented purely as CSS `:has()` relational selectors (`.lecture-content:has(.lecture-block.is-khas)` etc.) — `:has()` only shipped in Chromium 105 (mid-2022), and Xibo's Windows Player embeds Microsoft Edge WebView2, which is nominally auto-updating but on offline/locked-down signage hardware can sit on an old build indefinitely with **zero error, just a silently-unmatched selector** — everything else on the page (plain-class highlights like "Kuliah Hari Ini") kept working, which is exactly what made this a `:has()`-specific issue rather than a general rendering failure. **Lesson: any time you use a bleeding-edge CSS feature (`:has()`, container queries, `:is()`/`:where()` in older contexts, etc.) on a page destined for embedded/kiosk browsers you don't control the update cadence of, assume it might silently no-op there — either verify the actual runtime version, or avoid the feature and compute the equivalent decision in JS instead.** Fixed by moving the "does this cell contain Khas/Yasin, and is it sharing the cell with another session" decision into `buildDayCell()` (JS), which now derives `.has-khas`/`.has-yasin-solo`/`.has-yasin-shared` classes from the already-built HTML string via regex, and `style.css` matches on those plain classes. Verified against real live July 2026 data (not just synthetic test cases) via a `node -e` script loading `script.js` through `vm` and calling `buildDayCell()` directly — same harness style as `news/developer.md`'s documented convention. Full write-up: `kuliah/CLAUDE.md`'s "Desktop whole-cell purple/green highlight is computed in JS, not CSS `:has()`" Key Pattern.

1. **I misread my own dark-backdrop lightbox screenshots by eye, twice, in the same session — once for mobile, once for desktop — genuinely believing the overlay wasn't rendering when it actually was.** Both times the fix wasn't to the code, it was to how I was checking: `PIL`'s `getpixel()` at known coordinates (corners should read ~`rgb(36,37,37)` for `rgba(0,0,0,0.85)` over white) proved the backdrop was correctly covering the full viewport both times. **Lesson: for dark/low-contrast UI (overlays, backdrops, anything near-black), don't trust your own visual read of an attached screenshot — sample actual pixel values, or check computed styles (`getComputedStyle`) / DOM state directly.** This bit me enough times in one session that it's now a standing rule, not a one-off.
2. **A real image-load race condition in the *verification script*, not the shipped code:** screenshotting the desktop lightbox only 400ms after the click wasn't enough time for a 1920×1080 external poster JPG to fetch, decode, and paint — producing a screenshot that looked like a broken/empty dark overlay. The actual `initPosterLightbox()` code was correct the whole time (`img.src = ...` is synchronous and fires the network request immediately); only the test needed to explicitly await the image's `load` event / poll `img.complete && img.naturalWidth > 0` before calling `page.screenshot()`. **Lesson: never verify image-heavy UI with a fixed `waitForTimeout` — always await actual image-load completion, especially for external-domain images where fetch time varies.**
3. **A real CSS cascade bug caught and fixed *before* it ever shipped, by reasoning about it rather than by luck:** `.poster-lightbox[hidden] { display: none; }` had to be added explicitly. Without it, the author stylesheet's `.poster-lightbox { display: flex; }` would beat the browser's own default `[hidden] { display: none; }` user-agent rule — at equal specificity, author-origin CSS always wins ties over user-agent-origin CSS, so the `hidden` attribute alone would NOT have hidden the overlay, and the lightbox would have rendered open by default on every page load. Worth remembering any time a JS-toggled overlay uses the native `hidden` attribute alongside a `display` value other than `none` in its own base rule.
4. **A real invisible-UI bug that DID ship once, caught fast from a user screenshot:** the mobile Khas badge's pill background (`#f3e8ff`) was set to the exact same light purple as the box it sits inside (`.lecture-block-v2.is-khas`'s own background). A pill with zero contrast against its own container is literally invisible — the class/attribute wiring was 100% correct, the color choice just erased it visually. Fixed with a solid high-contrast color (`#9333ea` background, white text) instead of a light tint matching the container. **Lesson for any future badge/pill work in this codebase: check contrast against the immediate container background specifically, not just "does this color belong to the feature's palette."**
5. **The desktop poster-popup + hover-state additions were both cheap specifically because the mobile build had already generalized the lightbox correctly the first time** (`#poster-lightbox` + `initPosterLightbox()`'s delegated listener, written to be trigger-agnostic). Adding a second consumer (desktop `.lecture-block[data-poster-url]`) was a small, low-risk diff — confirms the "generalize the moment a second consumer needs the same pattern" house rule already documented in `admin/DEV_NOTES.MD` session 12 point 4, observed here in `kuliah/` for the first time.
6. **(Session 3, 2026-09-01) Two distinct bugs, both triggered only on the last few days of a month, both in `script.js`'s date math around `?bulan=depan` and the mobile "Hari Esok" dropdown — full technical write-up now lives in `kuliah/CLAUDE.md`'s "Month navigation & the two date-overflow bugs" Key Pattern, read it before touching this code again.** The short version: (a) `baseDate.setMonth(getMonth()+1)` without first pinning the day to 1 silently overflows into the month *after* next whenever today's day-of-month exceeds next month's day count (Aug 31 → October, not September) — `Date` never throws on this, it just quietly gives you the wrong month, which is exactly why it survived undetected until someone happened to test on Aug 31 specifically. (b) Separately, the mobile "Hari Esok" option computed the *correct* tomorrow-date (via `setDate(+1)`, which doesn't have the overflow problem — only `setMonth`+fixed-day does) but then looked it up only inside the currently-loaded month's cached day array, so on the last day of the month it always claimed "data not available yet" even when next month actually was published — the fetched JSON already had the answer sitting in `jsonData.months`, it just was never consulted. **Meta-lesson to carry forward: whenever you fix a `Date`-overflow or month-boundary bug in this file, don't stop at the one reported instance — grep for every other `setMonth`/day-array lookup nearby and check each one against the same day-29/30/31 edge case, because this codebase has now demonstrated the bug class shows up in more than one place at once.** Both fixes were minimal (a `setDate(1)` call; a new `cachedMonthsData` fallback lookup) — no architecture change needed, just correct handling of `Date`'s silent-overflow semantics.

### Session 3 (2026-09-01) — two month-boundary Date bugs in `kuliah/jadual/script.js`, both found and fixed same-turn

Opened cold (no prior context this window, VS Code had `kuliah/jadual/index.html` open) with a precise bug report: on 2026-08-31, `?bulan=depan` was showing October's table instead of September's. Diagnosed by reading `script.js`'s boot sequence directly — found `baseDate.setMonth(baseDate.getMonth() + 1)` running while `baseDate` still held day-of-month 31, which JS `Date` silently rolls over into October since September only has 30 days (see Unique Discoveries #6 for the full mechanism). Reported the cause and a proposed fix in prose only, per the standing diagnose-before-fix house rule — no code touched yet. User asked "so the edit will fix what?" — answered concretely with the before/after `Date` values (Aug 31 → overflow to Oct 1, vs. Aug 1 → clean Sept 1), not just a restatement of the diagnosis. User said "ok apply that fix" → added `baseDate.setDate(1)` before the `setMonth` call ([script.js:580-584](kuliah/jadual/script.js#L580-L584)).

User then asked, unprompted, what happens on Aug 31 if the visitor picks "Hari Esok" in the mobile dropdown — a self-directed check for a sibling bug in the same date-boundary territory, not something flagged proactively this time. Investigation found a *different* bug with the same trigger day: `tomorrowDate` itself was computed correctly (`setDate(+1)` doesn't have the overflow problem), but `renderTodayCard()`'s data lookup only ever searched the currently-loaded month's cached `senaraiHari` array — next month's day was never in it, so the card always fell into the `isTomorrow && !targetData` branch and showed "Data jadual untuk esok belum tersedia," regardless of whether September was actually published. Same rhythm: diagnosis reported first, user said "yes," then fixed by caching the full `jsonData.months` object (`cachedMonthsData`) and adding a cross-month fallback lookup ([script.js:12](kuliah/jadual/script.js#L12), [script.js:422-428](kuliah/jadual/script.js#L422-L428)).

Closed with this DEV_NOTES.MD update plus a sync pass on `kuliah/CLAUDE.md` (new Key Pattern documenting both bugs and the general lesson) and `kuliah/README.md` (added the previously-undocumented `?bulan=depan` query to the `jadual/` Access block).
